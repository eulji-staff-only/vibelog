# QA 따라하기 시나리오 만들기

QA하는 사람이 **무엇을 어디서 눌러서 무엇이 보이면 정상인지** 알 수 있게, 화면 하나의 확인 순서를 만든다.
답변은 한국어로, 쉬운 말로 쓴다.

## 먼저 읽을 것 (순서대로)

1. `docs/collaboration/09-qa.md` — 확인 방식, 계정, 이슈 올리는 법, 우선순위 기준. **이 문서가 기준이다.** (파일이 없으면 develop에 머지 전이므로 사용자에게 알린다)
2. 사용자가 말한 QA 이슈 (`gh issue view <번호>`) — 체크리스트에서 확인할 줄을 정한다. 번호를 모르면 묻는다.
3. `docs/design/01-screen-flow.md` — 그 화면 ID의 URL, 화면 구성, 모달, 이동 링크
4. **실제 코드** — 문구와 주소는 여기서 가져온다.
   - `src/main/resources/templates/<영역>/` 의 해당 템플릿: 버튼 이름, 탭 이름, 모달 제목, 안내 문구
   - `domain/<영역>/controller/`: 실제 URL, 비회원·권한 처리
   - `domain/<영역>/exception/<영역>ErrorCode`: 오류 문구
5. `docs/design/api/` 의 해당 영역 명세: 정상·실패 응답

`.env`는 읽지 않는다. 비밀번호는 문서에 없고 팀 채팅에 있으니 적지 않는다.

## 만드는 순서 (7단계, 항상 같은 형식)

1. **이슈를 확인한다** — 체크리스트의 어느 줄인지, 화면 ID, 주소
2. **준비하고 로그인한다** — 계정(비회원·학습자 `learner@vibelog.test`·운영자 `admin@vibelog.test`)과 필요한 데이터(예: 수강 시작해 두기). 시드(`sql/02-seed.sql`)에 있는 것만 쓴다
3. **정상 흐름** — 눌러야 할 것을 `a, b, c` 순서로. 각 단계에 **"보이면 정상 / 이상하면"** 을 적는다
4. **예외 흐름** — 아래 "예외 후보"에서 이 화면에 맞는 것만 고른다
5. **아쉬운 점 찾기** — 문구, 다음 행동 안내, 빈 상태, 클릭 수, 모바일 폭(약 400px)
6. **결과 기록** — 이상 없음 / 동작 문제(`🐛 버그 제보`) / 아쉬운 점(`🔧 작업`, 제목 `[개선]`, P3) / 보기 문제(`🔧 작업` + `🎨 design`)로 나누고, 어느 이슈에 번호를 적을지
7. 필요하면 **재현 방법 초안**을 `🐛 버그 제보` 양식 칸 순서로 적어 준다 (제목·재현 방법·기대·실제)

### 예외 후보 (화면에 맞는 것만)
- 빈 입력, 너무 긴 입력, 이미 있는 값
- 잠긴 화면, 조건 안 맞는 상태에서 주소 직접 입력
- 비회원·학습자·운영자로 같은 주소 열기 (권한)
- 로그아웃 후 열기, 새로고침, 뒤로 가기, 토스트가 두 번 나오는지
- 없는 번호의 주소 (404), 남의 데이터 주소

## 지켜야 할 것

- **문구·주소는 코드에서 확인한 것만 확정으로 쓴다.** 확인 못 한 것은 `(확인 필요)`를 붙인다. 기억이나 추측으로 쓰지 않는다.
- **설계서와 실제 화면이 다르면 그것도 결과에 적는다** (어느 쪽이 맞는지는 사람이 정한다).
- 예시 파일(`example.md`)의 화면 이름·문구·주소를 **그대로 베끼지 않는다.** 형식만 따른다.
- 시나리오만 만든다. 앱을 실행하거나 DB를 바꾸거나 이슈를 올리지 않는다. 이슈 올리기는 사용자가 시킬 때만 한다.
- 이 화면에서 **하지 않는 일**(다른 화면 범위)은 넣지 않는다. 필요해 보이면 "다른 화면에서 확인"이라고만 적는다.
- 한 번에 화면 하나. 체크리스트 여러 줄을 시키면 줄마다 따로 만든다.
- **클릭 단계는 구체적으로 쓴다.** "어디(메뉴·탭·카드)의 무엇(버튼·링크 이름)을 누르면 → 어디로 이동(주소)하거나 무엇이 나타난다"까지 적는다. "X 화면으로 간다"처럼 끝내지 않는다. 같은 이름의 버튼이 여럿이면 위치로 구분한다 (예: "첫 번째 카드의 수강 포기").

## 분량과 범위 (처음 하는 사람이 질리지 않게)

- 맨 위에 **"5분 핵심 코스"** 를 먼저 둔다: 정상 흐름 3~4개, 예외 흐름 2~3개만. 나머지는 "더 볼 것"으로 아래에 둔다.
- 이 화면에서 **바로 눌러 볼 수 있는 것**만 단계로 쓴다. 다른 화면의 작업이 먼저 필요한 상태(퀴즈 통과, 모의고사 제출, 코스 완료 등)는 단계로 만들지 말고 **"미리 필요한 상태" 한 줄**로 적는다. 시드로 만들 수 없으면 "미확인으로 두고 해당 화면 QA에서 만든 뒤 확인"이라고 쓴다.
- 같은 내용을 표와 목록으로 두 번 쓰지 않는다. 설계서와 다른 점은 한 곳(5번)에만 모은다.
- 비회원 권한 확인처럼 **로그인 전에 해야 하는 것**은 준비 단계(2번) 맨 앞에 둔다.

## 답변 끝에

- `(확인 필요)`로 남긴 것을 모아 목록으로 보여 준다. QA하는 사람이 눌러 보며 확인할 부분이다.
- 문서(`09-qa.md`)에 빠졌거나 헷갈리는 점이 있었으면 한 줄로 알려 준다 (QA 문서 개선용).

# 모드 2: QA 메모 정리 (이슈 초안 만들기)

사용자는 QA하면서 문제를 **메모장에 줄줄이 적어 두었다가 한꺼번에 붙여넣는다.** (하나씩 바로 올리면 채팅·이슈 목록이 밀리기 때문) 메모는 짧고 모호하다. 이슈로 만들기 전에 **부족한 정보를 먼저 되묻는다.**

## 순서

1. **줄마다 분류한다:** 동작 문제 / 아쉬운 점 / 보기 문제 / 질문·확인 필요. 분류가 애매하면 그것도 되묻는다.
2. **필수 정보가 빠졌는지 줄마다 점검한다:**
   - 화면 (화면 ID 또는 주소)
   - 계정 (비회원 / 학습자 / 운영자)
   - 무엇을 눌렀나 (어느 화면의 어떤 버튼·링크·탭, 이름 그대로)
   - 기대한 동작
   - 실제로 보인 것 (화면 문구, 오류, 콘솔)
   - 환경 (브라우저, 화면 폭) — 보기 문제일 때만
3. **빠진 것은 초안을 만들기 전에 묻는다.** 규칙:
   - 줄마다 번호를 붙여 **한 번에 모아서** 묻는다 (질문을 여러 번 나누지 않는다).
   - 추측해서 채우지 않는다. 코드·설계서로 **후보를 좁힐 수 있으면 후보를 보기로 준다.**
     - 예) 메모 "버튼이 안눌림" → "어느 화면인가요? 후보: ① 내 학습의 수강 포기 ② 같은 화면의 학습하기 ③ 다른 버튼. 눌렀을 때 아무 일도 없었나요, 오류가 떴나요?"
     - 예) 메모 "이상함" → "무엇이 기대와 달랐나요? 문구 / 이동 주소 / 숫자 / 모양 중 어느 것인가요?"
   - 대답이 "몰라"면 `(확인 필요)`로 두고 넘어간다. 계속 캐묻지 않는다.
4. **정리한다:**
   - 같은 원인으로 보이는 줄은 **하나로 묶는다.**
   - 올리기 전에 `gh issue list --search "<키워드>" --state all`로 **이미 있는 이슈**를 찾아 알려 준다 (읽기 전용).
   - 우선순위를 `09-qa.md` 4-4 기준으로 **제안**한다 (사람이 정한다).
   - 설계서·명세와 다른 줄은 따로 모아 "팀 결정 필요"로 표시한다.
5. **이슈 초안을 만든다:** `🐛 버그 제보` 칸 순서(제목·어떤 문제인가요·재현 방법·기대·실제·에러 메시지). 아쉬운 점은 `🔧 작업`, 제목 `[개선]`, P3. 보기 문제는 `🔧 작업` + `🎨 design`.
6. 스크린샷이 필요한 줄은 "스크린샷 첨부 필요"를 표시한다.

## 즉시 알려야 하는 것

메모 안에 **앱이 안 뜸, 로그인이 막힘, 핵심 학습 흐름이 막힘(P0)** 이 있으면 정리를 시작하기 전에 맨 위에 알린다. 모아서 보낼 일이 아니다.

## 하지 않는 것

- 이슈를 직접 올리지 않는다. 초안을 보여 주고 사용자가 시킬 때만 올린다.
- 사용자가 적지 않은 사실(재현 순서, 화면 문구)을 지어내지 않는다.
- 메모에 비밀번호가 있으면 초안에 옮기지 않는다.
