# 04. 이슈 규칙

[← 협업 규칙 README로 돌아가기](../../README.md)

---

## 왜 이슈부터 만드나요?

- **누가 무엇을 하는지** 한눈에 보여서 같은 일을 두 사람이 하는 일이 없습니다.
- **완료 조건**을 먼저 적어 두면, 만드는 사람과 리뷰하는 사람이 같은 기준으로 판단할 수 있습니다.
- 이슈 번호가 브랜치·PR과 연결되어 **"이 코드는 왜 생겼지?"** 를 나중에 추적할 수 있습니다.

> **규칙: 이슈 없는 브랜치, 이슈 없는 PR은 만들지 않습니다.** 오타 하나를 고치더라도 `🔧 작업` 이슈를 만들어 주세요. 30초면 됩니다.

---

## 이슈 양식 고르기

**Issues → New issue** 를 누르면 양식 4개와 기획 문서 바로가기가 나옵니다. (빈 이슈는 만들 수 없게 설정되어 있습니다.)

| 양식 | 이럴 때 | 제목 예시 |
|---|---|---|
| ✨ 기능 개발 | 요구사항 명세서의 기능(`FR-…`)을 구현할 때 | `[기능] 퀴즈 풀이·채점 (FR-LSN-006)` |
| 🐛 버그 제보 | 의도대로 동작하지 않는 것을 발견했을 때 | `[버그] 새로고침하면 로그아웃됨` |
| 🔧 작업 | 리팩터링 · 문서 · 설정 · 테스트 · 디자인 작업 | `[작업] 포트폴리오 카드 컴포넌트 분리` |
| 📐 요구사항 · 정책 변경 요청 | 명세서에 없는 기능 추가, 요구사항·정책 값·우선순위 변경, 문서끼리 안 맞을 때 | `[변경] 퀴즈 확인 문항 저장 방식 (PL-LSN-006)` |

> 💡 기능 이슈는 [요구사항 명세서](../planning/06-requirements.md)의 ID에서 시작합니다. 명세와 다르게 만들어야 하면 구현 전에 **📐 변경 요청**으로 팀 승인을 받으세요.

**제목 규칙:** `[양식] 무엇을 하는지` — 양식 머리말은 자동으로 들어가니, 뒤에 내용만 쓰면 됩니다.

## 좋은 이슈 쓰는 법

1. **크기는 1~3일 안에 끝낼 만큼.** "포트폴리오 기능 전체" 같은 큰 이슈는 쪼갭니다.
   - 큰 이슈는 상위 이슈로 두고, 이슈 화면의 **Create sub-issue** 로 작은 이슈들을 연결하세요.
2. **완료 조건을 구체적으로.** "잘 동작한다" ❌ → "정답률 50% 이상이면 통과 화면이 보인다" ⭕
3. **작업 목록은 체크리스트로.** `- [ ]` 형식으로 쓰면 진행률이 자동으로 표시됩니다.
4. **관련된 것은 링크로.** 기획서 위치, 디자인 링크, 관련 이슈(`#번호`)를 적어 주세요.

## 이슈를 만든 뒤 오른쪽 사이드바 채우기

| 항목 | 무엇을 넣나요 | 필수 |
|---|---|---|
| **Assignees** | 이 일을 할 사람 (아직 미정이면 비워 둠) | 작업 시작 시 필수 |
| **Labels** | 타입 라벨(자동) + 파트 + 영역 + 우선순위 | ⭕ |
| **Projects** | 팀 보드 | ⭕ |
| **Milestone** | 해당 마감 단위 (예: `1차 발표`) | 있으면 |

## 라벨 목록

라벨은 이슈를 **찾고, 거르고, 나누기** 위한 태그입니다. 아래 기준대로만 붙입니다.

### 타입 — 1개 (기능·버그는 양식이 자동으로 붙여 줌)

| 라벨 | 의미 |
|---|---|
| `✨ feature` | 새 기능 |
| `🐛 bug` | 버그 |
| `🎨 design` | 화면(UI)·CSS |
| `♻️ refactor` | 코드 구조 개선 |
| `✅ test` | 테스트 |
| `📝 docs` | 문서 |
| `🔧 chore` | 설정·패키지·빌드 |

### 우선순위 — 1개

| 라벨 | 의미 | 기준 |
|---|---|---|
| `P0: 긴급` | 지금 하던 일을 멈추고 처리 | 서비스를 쓸 수 없음, 발표·배포를 막음 |
| `P1: 높음` | 이번 마일스톤 안에 반드시 | 핵심 기능 |
| `P2: 보통` | 이번 마일스톤 안에 가능하면 | 기본값 |
| `P3: 낮음` | 여유 있을 때 | 개선·사소한 문제 |

### 파트 — 1개 이상

| 라벨 | 의미 |
|---|---|
| `part: FE` | 프론트엔드 |
| `part: BE` | 백엔드 |
| `part: 공통` | 설정·배포·문서 등 파트 구분 없는 작업 |

### 영역 — 1개 이상 (커밋 영역과 연결)

| 라벨 | 명세서 업무 코드 | 커밋 영역(scope) |
|---|---|---|
| `area: 회원` | USR | `auth` |
| `area: 진단·트랙·코스` | DGN, CRS | `course` |
| `area: 수강·수업·퀴즈` | ENR, LSN | `lesson`, `quiz` |
| `area: 모의고사·리포트` | EXM | `exam` |
| `area: 포트폴리오` | PRT | `portfolio` |
| `area: 커뮤니티·리뷰` | CMT, REV | `community` |
| `area: 콘테스트·배지` | CTS, RWD | `contest` |
| `area: 쪽지·신고·알림` | MSG, RPT, NTF | `message` |
| `area: 백오피스` | ADM | `admin` |
| `area: 공통·설정` | NFR · 인프라 | `common`, `config` |

### 상태 — 필요할 때만

| 라벨 | 언제 붙이나요 |
|---|---|
| `🌱 good first issue` | 처음 합류한 사람이 연습 삼아 하기 좋은 쉬운 이슈 |
| `🙋 help wanted` | 도움이 필요할 때 (담당자가 막혔거나 함께할 사람을 찾을 때) |
| `❓ question` | 결정이 필요한 질문 · 논의 |
| `⛔ blocked` | 다른 이슈·결정이 먼저 끝나야 진행 가능 (본문에 이유 적기) |
| `🔁 duplicate` | 이미 있는 이슈와 중복 (원래 이슈 번호를 댓글로 남기고 닫기) |

## 프로젝트 보드 사용법

저장소의 **Projects** 탭에서 팀 보드를 엽니다. 이슈 카드를 끌어서 옮기면 됩니다.

| 칸 | 의미 | 누가 언제 옮기나요 |
|---|---|---|
| 📋 Backlog | 언젠가 할 일 | 이슈를 만든 사람 |
| 📝 Todo | 이번 마일스톤에 할 일 | 회의에서 함께 정함 |
| 🏃 In Progress | 지금 하는 중 | 담당자가 작업을 시작할 때 |
| 👀 In Review | PR 올리고 리뷰 중 | 담당자가 PR을 올릴 때 |
| ✅ Done | 머지 완료 | PR이 머지되면 **자동으로** 이동 |

> 💡 **In Progress에는 1인당 이슈 1~2개만** 두세요. 여러 개를 동시에 붙잡으면 아무것도 끝나지 않습니다.

---

## 이슈 닫기

- 보통은 **PR 본문의 `Closes #12`** 덕분에 PR이 머지될 때 자동으로 닫힙니다.
- 하지 않기로 한 이슈는 **Close as not planned** 로 닫고, 이유를 댓글로 남깁니다.
- 닫힌 이슈를 다시 해야 하면 **Reopen** 하고 이유를 남깁니다.

## 간단한 질문은?

"이 API 이름 뭐로 할까요?" 같은 짧은 질문은 팀 메신저에서 해도 됩니다. 단, **결정된 내용이 나중에도 필요하면** `❓ question` 라벨을 붙인 `🔧 작업` 이슈로 남겨 두세요. 메신저 대화는 금방 묻힙니다.
