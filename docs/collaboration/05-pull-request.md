## Part 1. PR 올리는 사람

### PR 만들기 전 셀프 체크

- [ ] 최신 `develop`을 내 브랜치에 합쳤다 (`git merge develop`) — 충돌 없음
- [ ] 내 컴퓨터에서 직접 실행해서 동작을 확인했다
- [ ] `git diff develop`으로 변경 내용을 처음부터 끝까지 읽었다
- [ ] 이슈와 상관없는 변경, 디버그용 코드(`console.log`, `print`), 주석 처리된 죽은 코드가 없다
- [ ] `.env`, API 키, 비밀번호가 없다

### PR 제목

**커밋 규칙과 똑같은 형식**으로 씁니다. Squash merge 후 `develop`에 그대로 남는 이름입니다.

```
feat(quiz): 퀴즈 정답률 계산과 통과 판정 추가
```

| | 제목 | |
|---|---|---|
| ⭕ | `fix(auth): 새로고침하면 로그아웃되는 문제 수정` | |
| ❌ | `Feat/12 quiz grading` | 브랜치 이름을 그대로 둠 (GitHub 기본값이니 꼭 고치세요!) |
| ❌ | `12번 이슈 작업` | 무엇을 했는지 알 수 없음 |

### PR 본문

PR을 만들면 템플릿이 자동으로 채워집니다. 각 칸의 의미는 다음과 같습니다.

| 칸 | 무엇을 쓰나요 |
|---|---|
| 🔗 관련 이슈 | `Closes #12` — 머지되면 12번 이슈가 자동으로 닫힙니다. 여러 개면 `Closes #12, Closes #13` |
| 📌 작업 내용 | 무엇을 바꿨는지 목록으로 |
| 🔍 리뷰 포인트 | 리뷰어가 **특히 봐 줬으면 하는 곳**, 고민했던 부분, 자신 없는 부분 |
| 📸 스크린샷 | 화면이 바뀌었다면 전/후 캡처 또는 짧은 영상 (드래그해서 붙여넣기) |
| 🧪 확인 방법 | 리뷰어가 직접 확인해 볼 수 있는 순서 |
| 🤖 AI 활용 | (선택) 어떤 도구로 어느 부분을 만들었는지 |
| ✅ 셀프 체크리스트 | 하나씩 확인하고 `[x]` 체크 |

### PR 크기

- **변경 300줄 이하**를 권장합니다. 길어질수록 리뷰 품질이 떨어지고 버그를 놓칩니다.
- 커질 것 같으면 이슈를 쪼개서 PR을 여러 개로 나눕니다.
- 자동 생성 파일(패키지 lock 파일 등)은 줄 수에서 빼고 생각해도 됩니다.

### Draft PR 활용

작업이 덜 끝났지만 **방향이 맞는지 먼저 확인받고 싶을 때** Draft PR로 올리세요.
다 끝나면 PR 아래쪽 **Ready for review** 를 누르고 리뷰어를 지정합니다.

### 리뷰어 지정

- **자동으로 지정됩니다.** 기본 리뷰어는 PM(`dyryoo316`)과 형상관리(`SeungBinYang`)이고, 둘 중 1명이 승인해야 머지할 수 있습니다 (`.github/CODEOWNERS`).
- **영역 간 연동 PR** — 다른 묶음 담당 영역의 파일이나 `sql/`을 바꾸면 `area-review` 검사가 그 영역 담당(또는 DB 팀)을 리뷰어로 추가하고, **그 사람의 승인까지** 받아야 머지 버튼이 열립니다.
- 자세한 표는 [README "리뷰어 지정 약속"](../../README.md#-코드-구조-규칙)을 보세요.

## Part 2. 리뷰하는 사람

### 응답 시간

- 리뷰 요청을 받으면 **24시간 안에 첫 응답**을 합니다.
- 바로 볼 수 없으면 댓글로 "내일 오전에 볼게요"라고 남겨 주세요. 작성자가 기다리는 동안 다음 계획을 세울 수 있습니다.

### 리뷰하는 방법 (GitHub 화면)

1. PR의 **Files changed** 탭을 엽니다.
2. 의견을 남길 줄 번호 옆 **`+`** 를 누르고 코멘트를 씁니다. → **Start a review** (첫 코멘트) / **Add review comment** (그다음부터)
3. 다 봤으면 오른쪽 위 **Finish your review** (또는 **Review changes**)를 누르고 셋 중 하나를 고릅니다.

| 선택 | 언제 |
|---|---|
| **Comment** | 질문·의견만 남기고 판단은 보류할 때 |
| **Approve** | `[필수]` 코멘트가 없을 때 → 머지해도 좋다 |
| **Request changes** | `[필수]` 코멘트가 하나라도 있을 때 → 고쳐야 머지 가능 |

> 💡 **바뀐 화면을 직접 확인하고 싶다면** 내 컴퓨터에서 `git fetch` → `git switch feat/12-quiz-grading` 으로 그 브랜치를 받아 실행해 볼 수 있습니다. 확인 후엔 `git switch develop`으로 돌아오세요.

### 코멘트 머리말 규칙

모든 리뷰 코멘트 맨 앞에 머리말을 붙입니다. 작성자가 **무엇을 꼭 고쳐야 하는지** 바로 알 수 있습니다.

| 머리말 | 의미 | 예시 |
|---|---|---|
| `[필수]` | 고치지 않으면 머지 불가 (버그, 보안, 규칙 위반) | `[필수] 문제 수가 0이면 0으로 나누게 돼요. 0일 때 처리를 추가해 주세요.` |
| `[제안]` | 고치면 더 좋음. 작성자가 판단 | `[제안] 이 계산은 다른 곳에서도 쓸 것 같은데 유틸로 빼면 어떨까요?` |
| `[질문]` | 이해가 안 돼서 묻는 것 | `[질문] 통과 기준을 여기서 50으로 직접 쓴 이유가 있을까요?` |
| `[칭찬]` | 좋은 점 | `[칭찬] 경계값 테스트까지 꼼꼼하게 넣어 주셨네요 👍` |

### 무엇을 보나요? (리뷰 체크리스트)

1. **이슈의 완료 조건**을 모두 만족하나요?
2. **동작**: 예외 상황(빈 값, 0, 아주 긴 값, 로그인 안 한 상태)에서 깨지지 않나요?
3. **보안**: 비밀 키·개인정보가 코드나 로그에 노출되지 않나요? 사용자 입력을 그대로 믿고 쓰지 않나요?
4. **범위**: 이슈와 상관없는 변경이 섞이지 않았나요?
5. **읽기 쉬움**: 이름만 보고 무엇을 하는지 알 수 있나요?
6. **규칙**: PR 제목, 브랜치 이름이 규칙에 맞나요?

### 말투 원칙

- **코드를 이야기하고, 사람을 평가하지 않습니다.** "왜 이렇게 짰어요?" ❌ → "이 부분은 ○○ 상황에서 문제가 생길 수 있을 것 같아요" ⭕
- **이유와 대안을 함께** 적습니다. "이거 별로예요" ❌ → "○○ 때문에 △△ 방식이 더 안전할 것 같아요" ⭕
- **질문은 진짜 질문으로.** 모르는 건 부끄러운 게 아닙니다. 초보자의 질문이 숨은 버그를 찾기도 합니다.
- **잘한 점도 꼭 말해 주세요.** `[칭찬]` 하나가 팀 분위기를 바꿉니다.

## Part 3. 리뷰를 받은 뒤

1. `[필수]`는 반드시 반영하고, `[제안]`은 반영하거나 반영하지 않는 이유를 답글로 남깁니다.
2. 반영은 **같은 브랜치에 커밋을 추가하고 push** 하면 됩니다. PR이 자동으로 업데이트됩니다.
3. 각 코멘트에 답글을 남깁니다. 예: `반영했습니다! (a1b2c3d)`
4. **Resolve conversation** 은 **코멘트를 남긴 리뷰어가** 확인 후 누릅니다. (리뷰어가 직접 확인했다는 표시)
5. 다 반영했으면 Reviewers 옆 🔄 버튼으로 다시 리뷰를 요청합니다.
6. 의견이 갈려 결론이 안 나면 코멘트로 길게 다투지 말고, **짧게 통화하거나 팀 회의에서 결정**한 뒤 결과를 PR에 남깁니다.

## Part 4. 머지

### 머지 조건 (모두 만족해야 함)

- [ ] Approve **1개 이상**
- [ ] `[필수]` 코멘트가 모두 해결됨 (모든 conversation이 Resolved)
- [ ] 충돌 없음
- [ ] (자동 검사가 생기면) 모든 검사 통과 ✅

### 누가, 어떻게

- **PR 작성자가 직접** 머지합니다. 내 코드가 들어가는 순간을 내가 책임집니다.
- `develop`으로 가는 PR은 항상 **Squash and merge**.
- 머지 직전 확인: 커밋 메시지 첫 줄이 **PR 제목과 같고 규칙에 맞는지**.
- 머지 후 브랜치가 자동 삭제되지 않았다면 **Delete branch** 를 누릅니다.

### 머지 방식 정리

| PR 방향 | 머지 방식 | 이유 |
|---|---|---|
| 작업 브랜치 → `develop` | **Squash and merge** | PR 하나가 커밋 하나로 남아 `develop` 기록이 깔끔 |
| `develop` → `main` (배포) | **Create a merge commit** | 어떤 배포에 무엇이 들어갔는지 경계가 남음 |
| `hotfix/…` → `main` | **Squash and merge** | 긴급 수정 하나 = 커밋 하나 |
| `main` → `develop` (hotfix 반영) | **Create a merge commit** | 두 브랜치의 기록을 그대로 맞춤 |
| (사용 안 함) | ~~Rebase and merge~~ | 저장소 설정에서 꺼져 있음 |

### 머지 후에 문제가 생겼다면

머지된 PR 화면 아래의 **Revert** 버튼을 누르면 그 변경을 되돌리는 PR이 자동으로 만들어집니다. 일반 PR처럼 승인받고 머지하면 됩니다. **혼자 `develop`을 강제로 되돌리지 마세요.**
